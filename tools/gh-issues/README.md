# gh-issues

Заводит задачи GitHub из файла задач `ISSUES-<тема>.md` так, чтобы ничего не забылось: у каждой задачи
есть исполнитель и приоритет, она лежит на доске проекта со статусом, а ссылка на неё вписана обратно в
файл. Без флага `--apply` только проверяет и показывает план. Пара к скилу `file-issues`
(`.claude/skills/file-issues/`), в котором описано, кому назначать задачу и какой ставить приоритет.

```bash
python tools/gh-issues/gh_issues.py ISSUES-тема.md               # план: проверки, ничего не создаёт
python tools/gh-issues/gh_issues.py ISSUES-тема.md --apply       # завести задачи из плана
python tools/gh-issues/gh_issues.py ISSUES-тема.md --only 2,3    # только разделы 2 и 3
python tools/gh-issues/gh_issues.py set org/repo#123 --priority High            # план правки уже заведённой
python tools/gh-issues/gh_issues.py set org/repo#123 --priority High --apply    # записать
python tools/gh-issues/gh_issues.py --version
```

`--apply` — действие наружу: запускать только после «да» пользователя на показанный план.

## Что нужно

- Python 3.9+ (только стандартная библиотека).
- [GitHub CLI](https://cli.github.com/) `gh`, вход с правами `repo`, `project`, `read:org`:
  `gh auth login --hostname github.com --git-protocol https --web --scopes project`.
- `config.local.json` рядом со скриптом (пример — `config.example.json`).

## Настройки

`config.local.json` (другой путь — `--config` или переменная `GH_ISSUES_CONFIG`):

| Поле | Обязательно | Что задаёт | По умолчанию |
| --- | --- | --- | --- |
| `org` | да | Организация GitHub: в ней поле приоритета и доска; `[svc]` в заголовке → `<org>/svc` | — (без него выход с кодом 2) |
| `project` | нет | `{"number": N}` — доска организации, куда кладётся карточка | `null` — без доски |
| `default_status` | нет | Статус карточки, если доска не поставила его сама | пусто — не ставить |
| `priority_field` | нет | Имя поля организации (issue field) с приоритетом | `Priority` |
| `required` | нет | Что обязано быть у задачи: `assignee`, `priority` | оба |
| `repo_from_title` | нет | Брать репозиторий из префикса `[svc]`, если строки «Репо» нет | `true` |
| `gh` | нет | Путь к `gh`, если его нет в `PATH` | поиск в `PATH`, затем `C:\Program Files\GitHub CLI\gh.exe` |
| `timeout_s` | нет | Предел на один вызов `gh`, секунды | `120` |

Переменные окружения (все необязательные): `GH_ISSUES_CONFIG` — путь к настройкам; `GH_ISSUES_GH` — путь к
`gh` (сильнее `gh` из настроек); `GH_ISSUES_DEBUG=1` — показывать трейсбек при сбое. Секретов скрипт не
хранит и не читает: доступ к GitHub — у `gh`.

## Формат файла задач

```markdown
## 1. [payload-back] Login form says "Invalid credentials" when the account is locked

Репо: `org/payload-back` · Исполнитель: @login · Приоритет: High · Метки: bug

**Что происходит.** …
**Где воспроизведено.** qa2 22.10.2026: …

---
```

- Задача — раздел `## ` с заголовком, который (после необязательного номера `N.`) начинается с `[`.
  Остальные разделы (`## Сводка`, `## Предположения`) — не задачи.
- Строки метаданных идут сразу под заголовком: в одной строке через ` · ` или каждая отдельно. Ключи —
  `Репо`/`Repo`, `Исполнитель`/`Assignee` (несколько — через запятую), `Приоритет`/`Priority` (вариант поля
  организации, регистр не важен), `Метки`/`Labels`, `Статус`/`Status` (колонка доски, если нужна не
  колонка по умолчанию), `Задача`/`Issue` (ставит сам скрипт).
- Всё ниже метаданных до следующего `## ` — текст задачи (без замыкающего `---`).
- После создания скрипт вписывает `Задача: <ссылка>` под метаданные. Раздел со ссылкой повторный запуск
  пропускает; ссылка пишется сразу после создания, до остальных шагов.

## Что проверяется до записи

План (и `--apply` перед записью) проверяет каждую задачу и при любой ошибке ничего не создаёт:
репозиторий есть и в нём включены задачи; есть исполнитель и приоритет (если требуются); исполнителя
можно назначить в этом репозитории; метки существуют (создавать их скрипт не будет); такой вариант
приоритета есть у поля организации; такой статус есть на доске; нет задачи с тем же заголовком (флаг
`--allow-duplicate` снимает эту проверку); в тексте нет голых маркеров `[R]`/`[C]`/`[T]`/`[A]`/`[?]` —
задачу читают разработчики, основания пишутся словами.

## Что делает `--apply`

Для каждой задачи по очереди: `gh issue create` (заголовок, текст из временного файла, исполнители,
метки) → ссылка в файл → приоритет мутацией `setIssueFieldValue` → карточка на доске
(`gh project item-add`) и статус, если доска сама его не поставила (`gh project item-edit`) → сверка:
перечитывает задачу и сравнивает исполнителей, метки, приоритет и статус с запрошенным. Что не
записалось, печатается строкой `✗`, код выхода 1; задача при этом уже создана, а дописать недостающее
можно командой `set`. Повторов при ошибке нет: создание задачи не идемпотентно.

Приоритет — поле организации (issue field), а не метка и не поле доски: колонка Priority на доске
показывает это же поле, своих вариантов у неё нет.

Скрипт не меняет настройки доски и полей организации, не создаёт метки, не закрывает и не правит чужие
задачи, кроме `set` на названной задаче.

## Коды выхода

`0` — план чистый / всё записано; `1` — ошибки в задачах, сбой `gh` или часть полей не записалась;
`2` — ошибка запуска (нет файла, настроек, `gh`).

## Тесты

```bash
python tools/gh-issues/tests/test_gh_issues.py
```

Без сети: вместо `gh` — подмена в памяти (задачи, метки, поле приоритета, доска). Проверяются разбор
файла, ошибки плана без единой записи, создание с исполнителем, приоритетом и карточкой, сохранение
статуса, который поставила доска, вписывание ссылки и пропуск при повторе, сбой приоритета, `set`.
Живая запись в GitHub тестами не покрыта — её проверяет первый запуск с `--apply`.
