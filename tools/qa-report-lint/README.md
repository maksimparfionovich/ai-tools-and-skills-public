# qa-report-lint

Механическая проверка того, что вердикты в QA-отчёте и тест-плане опираются на основание: `PASS` —
только по реальному прогону, у бага — причина в коде и происхождение (внесён веткой или был раньше),
у отчёта — тест-план, у каждого кейса плана — вердикт. Проверяет механику, не семантику: качество
самих проверок остаётся на авторе. Содержательные правила — скил `qa-evidence`.

Только стандартная библиотека Python 3.8+. Шаблоны плана и отчёта — `templates/`.

## Запуск

```bash
python3 tools/qa-report-lint/lint.py <файл.md> [...]   # exit 1 при ошибках
python3 tools/qa-report-lint/lint.py --explain          # памятка по правилам
python3 tools/qa-report-lint/lint.py --config my.json <файл.md>
```

На Windows — `python` вместо `python3` (в Git Bash `python3` часто оказывается заглушкой Microsoft Store).

Регресс самого линтера — `bash tools/qa-report-lint/tests/run.sh` (фикстуры в `tests/`; интерпретатор
выбирается сам, ваши настройки на тесты не влияют).

## Хук: проверка при каждой записи отчёта

Подключается как `PostToolUse`-хук на `Write|Edit`: агент записал `.md` — линтер проверил его и при
ошибках вернул код 2, агент видит ошибки и правит файл. В `.claude/settings.json` проекта:

```json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit|MultiEdit",
        "hooks": [{ "type": "command",
                    "command": "python3 \"${CLAUDE_PROJECT_DIR}/tools/qa-report-lint/lint.py\" --hook",
                    "timeout": 20 }] }
    ]
  }
}
```

На Windows — `python` и абсолютный путь к `lint.py` с прямыми слешами.

Хук проверяет только `.md` в папках из `hook_dirs` (по умолчанию — только корень проекта): документация
внутри вложенных репозиториев пишется по чужим правилам. Файлы `CLAUDE.md`, `AGENTS.md`, `SKILL.md`,
`README.md`, `MEMORY.md` не проверяются. Ручной запуск из командной строки ограничений не имеет.

## Настройка

Без настроек работают значения по умолчанию. Свои — в `config.local.json` рядом с `lint.py` (пример —
`config.example.json`), в файле из переменной `QA_LINT_CONFIG` или через `--config`:

| Поле | По умолчанию | Что задаёт |
| --- | --- | --- |
| `root` | пусто | Корень проекта. Пусто — `$CLAUDE_PROJECT_DIR`, затем `cwd` из JSON хука, затем папка на два уровня выше `lint.py` |
| `hook_dirs` | `["."]` | Папки относительно корня, где хук проверяет `.md` |
| `skip_files` | `CLAUDE.md`, `AGENTS.md`, `SKILL.md`, `README.md`, `MEMORY.md` | Имена файлов, которые хук не проверяет |
| `stands` | `[]` | Имена стендов проекта (регулярные выражения) в дополнение к встроенным: `devN`, `qaN`, `stageN`, `uatN`, `staging`, `uat`, `prod`/`прод`, `local`/`локально`. Нужны правилу E3 и подписи прогона словами |
| `dimensions` | девять измерений (см. E12) | Свой набор измерений «Покрытия»: `[["Название", "начало первой ячейки"], …]` |

Какой файл считается отчётом, а какой тест-планом, — по имени: отчёт — `qa-*`, `bug-*`, `bugs-*`,
`review-*`, `testrun-*`, `report-*` или слово `report`/`отчёт` в имени; план — `testplan-*` или
файл с не-отчётным именем, у которого в первом заголовке «тест-план».

## Что считается вердиктом

Только токен, стоящий ПЕРВЫМ в ячейке таблицы или сразу после `Статус:` /
`Вердикт:` / `Итог:`. Проза, логи и содержимое ``` -блоков вердиктами не
считаются — чтобы правило не мешало писать связный текст. Исключение — два
правила, которые смотрят на прозу: E7 (находка описана в тексте, но не вынесена
в таблицу) и W2 (утверждение о причине без основания; только предупреждение).

Токены: `PASS | FAIL | FAIL_EXPECTED | PARTIAL | NOT_VERIFIED | BLOCKED | STOP | N/A`.
`FAIL_EXPECTED` — baseline «до фикса» (red-доказательство); не блокирует итоговый PASS.

Маркеры основания: `[T]` требование · `[C]` код · `[R]` прогон · `[A]` предположение · `[?]` не проверено.

Отчёты читают разработчики, поэтому каждый маркер можно (и в тексте для них — нужно) писать
**подписью словами** в начале фрагмента, с двоеточием. Подпись засчитывается как маркер во всех
правилах (E1–E4, E8, E9, E14, W2):

| Маркер | Подпись словами |
| --- | --- |
| `[R]` | «Воспроизведено / Не воспроизводится / Проверено / Проверил / Прогон / На проде / На стенде … `<стенд>` или `<дата>`:» — без стенда и даты в подписи прогоном не считается |
| `[C]` | «В коде:», «По коду:», «Причина в коде:», «Место в коде:», «Код:» |
| `[T]` | «Требование:», «По тикету:», «Тикет …:», «По спеке:», «Спецификация:» |
| `[A]` | «Предположение:», «Догадка:», «Гипотеза:» |
| `[?]` | «Не проверено:», «Не удалось …:», «Причина в коде не найдена:», «Нет доступа:», «Недоступно:» |

Фрагменты делятся по `;`, `|`, `·`, « — », «. », «(»; подпись должна стоять в начале фрагмента, а
двоеточие — в пределах 60 символов и не внутри `обратных кавычек`. Дата — `2026-10-13` или `13.10[.2026]`.
Буквы `[R]`/`[C]`/… допустимы только с расшифровкой в том же файле (E15).

## Правила

| Код | Проверка |
| --- | --- |
| E1 | вердикт без маркера основания (итоговый вердикт исключён — он агрегат таблицы) |
| E2 | `PASS` без `[R]`: фактического прогона нет |
| E3 | `[R]` без контура и даты (ищутся в строке или в шапке файла) |
| E4 | `[C]` без `path:line` или SHA |
| E5 | итоговый `PASS` при открытых `FAIL`/`BLOCKED`/`STOP` |
| E6 | `NOT_VERIFIED`/`BLOCKED` без причины |
| E7 | находка `F-n`/`BUG-n`, определённая в прозе (заголовок `### F-1`, абзац/пункт `**F-1 …`), без строки таблицы, где ID — первая ячейка (допустимы `` `F-1` ``, `**F-1**`, `🛑 F-1`). Упоминание внутри текста или в другой ячейке определением не считается. Снятая находка тоже получает строку (`N/A`) |
| E8 | `FAIL` (не `FAIL_EXPECTED`) без причины в коде. Проходит: `[C]` (причина найдена) **или** одновременно `[?]` с пояснением («причина в коде не найдена, потому что …») и `[A]` с догадкой. Только догадка или только «не найдена» — ошибка. Итоговый вердикт (агрегат) исключён. Формат `[C]` (path:line) проверяет E4 |
| E9 | `FAIL` (не `FAIL_EXPECTED`, не итоговый) без происхождения: баг ветки или легаси. Значение — в колонке таблицы с шапкой «Происхождение» (или «Ветка/легаси») **или** в строке `Происхождение: <значение>`; допустимы `ветка`, `легаси`, `легаси+ветка`, `не установлено`. Для первых трёх в строке нужны `[C]` или `[R]` и названная база сравнения (`main`/`master`, прод, `baseline`/базовый, `diff`, `blame`, `merge-base`, `git show/log`, диапазон `<sha>..<sha>`, `release-N`/релиз, `PR #N`, «без/до ветки/фикса») — либо ссылка на находку (`см. F-1`), у которой происхождение обосновано. `не установлено` — `[?]` и `[A]` с пояснениями |
| E10 | отчёт (файл с «отчётным» именем — как у W0 — и с вердиктами) без тест-плана: нет строки `Тест-план: <файл>.md`, нет раздела `## Тест-план` (уровень `##` и ниже) и нет `Тест-план: N/A — <почему>` с причиной. Ссылка на несуществующий файл — тоже E10. Путь ищется относительно отчёта, затем корня проекта |
| E11 | кейс тест-плана без вердикта: ID кейса из плана нет первой ячейкой ни в одной таблице отчёта, и в самой строке плана вердикта тоже нет (результат можно вести колонкой в плане). Файлы багов (`BUGS-*`, `bug-*`, `bugreport-*`) E11 не проверяет — там только открытые дефекты |
| E12 | в тест-плане нет «Покрытия»: таблицы в разделе «Покрытие» или таблицы с шапкой «Измерение \| …»; нет строки одного из измерений (по умолчанию девять; первая ячейка начинается с: Требования, Изменения в коде, Негатив, Локали, Регион, Окружение, База, Регресс, Интерфейс; свой набор — поле `dimensions` настроек); у измерения нет ни ID кейса из таблицы кейсов, ни `N/A — <причина>` (причина ≥ 8 значимых символов) |
| E13 | в тест-плане нет блока «Контекст проверки» (можно внутри ``` -блока) или в нём нет пункта списка `- env: …` |
| E14 | в файле тест-плана нет таблицы кейсов (шапка начинается с `ID` / `Check ID` / `Кейс` и содержит колонку «Ожидание») или у кейса нет источника — маркера `[T]`/`[C]`/`[A]`/`[?]`/`[R]` |
| E15 | маркеры буквами без расшифровки: в файле встречается `[R]`/`[C]`/`[T]`/`[A]`/`[?]` (где угодно вне ``` -блоков), а расшифровки этого маркера нет — ни строки вида «[R] — проверено прогоном на стенде» вне таблиц проверок и строк `Статус:` (обычно в шапке: «Обозначения: …»), ни строки таблицы `\| [R] \| <пояснение> \|`. Разработчику голые буквы ничего не говорят: либо расшифровка, либо основание словами |
| E16 | у `FAIL` голая метка происхождения `ветка` / `легаси` / `легаси+ветка` (в т. ч. `LEGACY`), а в файле нет её расшифровки — ни строки вида «легаси — дефект есть и без ветки …» (разделитель `—`/`–`/`=`/` - `, пояснение ≥ 8 букв; вне таблиц проверок и строк `Статус:`), ни строки таблицы `\| легаси \| <пояснение> \|`. Не считается голой: метка с пояснением словами в той же строке («легаси — есть и без ветки», «легаси (есть и без ветки)») и происхождение сразу словами: «внесён / внесла веткой», «появился в ветке» = `ветка`; «есть и без ветки», «было и до ветки», «есть и на main/проде» = `легаси`; «старая причина … ветка проявила/усилила» = `легаси+ветка`. `не установлено` расшифровки не требует — его поясняют `[?]` и `[A]` |
| W0 | у файла с «отчётным» именем нет вердиктной таблицы (предупреждение) |
| W1 | `PASS` с оговоркой «в пределах доступного / частично» — это `PARTIAL` |
| W2 | утверждение о причине без основания в той же строке (предупреждение, exit code не меняет; раздел «Предположения» и ``` -блоки не проверяются). Группа 1 «атрибуция причины» — `поведение Payload/Nuxt/Next/React/Vue/библиотеки/фреймворка`, `баг Payload/…`, `причина —/:`, `из-за` — требует `[C]` (или `path:line`), `[A]` или `[?]`. Группа 2 «было и до фикса» — `не из этого PR/фикса/ветки`, `есть/было/воспроизводится и без фикса`, `pre-existing`, `до фикса тоже` — требует `[R]`, `[C]` или `[A]` |

### Как читать E7 / E8 / E9 / W2

Правило команды: у каждого бага названа причина в коде — либо честно сказано,
почему она не установлена. Формулировка «это поведение Payload» без `[C] path:line`
причиной не является: это гипотеза, её место — `[A]` (и раздел «Предположения»).

- **E7.** Находка, описанная прозой в разделе «Находки», но без строки в таблице,
  вердиктом не является, и линтер её не видит. Вынеси в таблицу: `ID | суть | вердикт | основание`.
- **E8.** `FAIL` = дефект, у дефекта есть причина. Назови её (`[C] src/x.ts:88`). Если не
  нашёл — обозначь это явно и дай догадку, оба маркера сразу:
  `[?] причина в коде не найдена, потому что … ; [A] догадка: …`. Одна догадка без явного
  «не найдена» выглядит как объяснение и останавливает поиск; одно «не найдена» без догадки
  не даёт, от чего оттолкнуться. `FAIL_EXPECTED` (baseline «до фикса») причины не требует.
- **E9.** Про каждый баг сразу понятно, внесла его проверяемая ветка или он
  был и без неё. Колонка «Происхождение» в таблице находок — основная форма (шаблон); в таблице
  проверок, где колонки нет, — `Происхождение: ветка — см. F-1`. В колонковой форме метка
  `происхождение: [C] …` внутри ячейки основания — подпись основания, а не значение.
  Значения:
  - `ветка` — на базе (main, точнее `git merge-base`, или прод) дефекта нет; в отчёте без
    проверяемой ветки (аудит прода, инцидент) — дефект внесён названным релизом/PR;
  - `легаси` — есть и без ветки: та же причина **и тот же путь к ней** на базе;
  - `легаси+ветка` — причина старая, но ветка её проявила (сделала достижимой) или усилила последствия;
  - `не установлено` — сравнить с базой не удалось: `[?] почему` + `[A] догадка`, как в E8.

  Линтер видит, что база **названа**, но не что сравнение сделано: `[R] prod …` в строке
  аудита прода формально проходит и как основание «легаси». Это механика, а не семантика —
  содержательное правило в скиле `qa-evidence`.
- **W2.** Маркер должен стоять в той же строке файла (для таблиц — в той же строке
  таблицы). Обратные кавычки при поиске фраз игнорируются (цитата UI/кода).

### Как читать E10–E14 (тест-план)

Любое тестирование начинается с тест-плана — до первого прогона, сразу после блока «Контекст
проверки». Содержательное правило — скил `qa-evidence`, раздел «Тест-план»; шаблон —
`templates/testplan.md`. Линтер проверяет механику:

- **Файл плана** — `TESTPLAN-*.md` (или файл с не-отчётным именем, у которого в первом заголовке
  «тест-план»). В нём: блок «Контекст проверки» с пунктом `- env: …` (E13), таблица кейсов с
  источником (E14), «Покрытие» по всем измерениям (E12).
- **Отчёт** ссылается на план: `Тест-план: TESTPLAN-<тема>.md` в шапке (E10), и каждый кейс плана
  получает вердикт — строкой в таблице отчёта, где ID кейса = Check ID, или колонкой результата в
  самом плане (E11). Снятый кейс — тоже строка (`N/A` с причиной).
- **Разовая проверка** может держать план внутри отчёта: раздел `## Тест-план` с блоком контекста и
  таблицей «Измерение | Кейсы или N/A — почему»; кейсы — это строки таблицы проверок того же отчёта.
- **Отчёт без прогона** (ревью кода, разбор) пишет `Тест-план: N/A — <почему>`.

Линтер видит, что измерение **заполнено**, а не что кейсы хорошие: «N/A — не нужно» с восемью
буквами формально проходит. Качество плана — на авторе и на скиле.


## Калибровка

Правила калибровались на ~250 реальных отчётах и тест-планах: ложные срабатывания на живой прозе
устранены (`` `failed: []` `` не читается как `FAIL`, «из-за» в обычной прозе не считается утверждением
о причине, дата `09.09.2026` засчитывается, слова «наблюдать»/«замер» не считаются подписью прогона).
Оставшиеся известные ложные срабатывания W2 — единицы, это только предупреждения: отрицание («не
обязательно баг библиотеки»), ссылка на причину в другом месте («причина — в бэкенде, см. B3»),
ожидаемый результат в тест-плане.

Старые отчёты, написанные до правил, дают ошибки массово — это нормально: хук срабатывает только при
новой записи файла, разовой правки старых файлов не требуется.
