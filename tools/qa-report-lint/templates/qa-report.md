# <Тема> — QA-отчёт

Контур: <стенд: qa1 | staging | prod | local …>, `<базовый URL>`.
Дата: <YYYY-MM-DD>. Ветка/SHA: front `<sha>`, back `<sha>`.
База для «ветка или легаси»: main `<sha merge-base>` / прод `<release-N>` (для отчёта без ветки — предыдущий релиз).
Источник требований: <тикет / PR / спека / «письменного требования нет — критерий выведен из кода»>.
Тест-план: `TESTPLAN-<тема>.md` (шаблон `templates/testplan.md`; для разовой проверки — раздел `## Тест-план` здесь же; отчёт без прогона — `N/A — <почему>`). Баги: `BUGS-<тема>.md`. Прогресс: `PROGRESS-<тема>.md`.

Отчёт читают разработчики, поэтому основание пишется словами: «Воспроизведено на qa2 13.10: …»,
«В коде: `path:line`», «Требование: …», «Предположение: …», «Не проверено: …». Если в сводной таблице
удобнее буквы, в шапке нужна строка «Обозначения: [T] — требование, [C] — место в коде, [R] — проверено
прогоном на стенде, [A] — предположение, [?] — не проверено». Описание бага и «Статус» — всегда словами.

Происхождение: ветка — дефект внесён проверяемой веткой, на main и проде его нет; легаси — дефект есть и без ветки, на main или проде; легаси+ветка — старая причина, которую ветка проявила или усилила.

## Проверки

Check ID = ID кейса из тест-плана. Каждый кейс плана — строка здесь, снятый тоже (`N/A` с причиной).

| Check ID | Проверка | Вердикт | Основание |
| --- | --- | --- | --- |
| `c1` | <что проверяется> | PASS | Воспроизведено на <стенд> <дата>: <что открыто и что видно> |
| `c2` | <что проверяется> | NOT_VERIFIED | По коду: `path/file.ts:88` — ожидается X; Не проверено: <почему прогон недоступен> |
| `c3` | <что проверяется> | FAIL | Требование: AC-N тикета; Воспроизведено на <стенд> <дата>: <фактический результат>; В коде: `path/file.ts:88` — <причина> (если не найдена: Причина в коде не найдена: <почему>; Догадка: <…>); Происхождение: ветка — см. F-1 |
| `c4` | <что проверяется> | BLOCKED | Не проверено: <что именно блокирует: нет доступа/кредов/общий стенд без согласия> |

**Вердикт:** <PASS | FAIL | PARTIAL> — <одна строка>.

## Находки

Каждая находка (`F-1`, `BUG-1` …), описанная в тексте ниже, обязана иметь строку в таблице:
ID | суть | вердикт | происхождение | основание. Снятая находка тоже получает строку (`N/A`).

У каждого `FAIL` — происхождение, и его основание стоит в ячейке «Основание» рядом с причиной.
Метка без строки «Происхождение: …» в шапке разработчику непонятна (E16): держи строку в шапке или пиши
словами — «внесён веткой», «есть и без ветки», «старая причина, ветка проявила». Значения:

- `ветка` — внесён проверяемой веткой: на базе дефекта нет (для отчёта без ветки — внесён названным релизом/PR);
- `легаси` — есть и без ветки: та же причина и тот же путь к ней в main или на проде;
- `легаси+ветка` — причина старая, но ветка её проявила или усилила последствия;
- `не установлено` — «Не проверено: почему сравнить с базой не удалось» + «Догадка: …».

| ID | Суть | Вердикт | Происхождение | Основание |
| --- | --- | --- | --- | --- |
| `F-1` | <суть находки> | FAIL | ветка | Воспроизведено на <стенд> <дата>: <результат>; В коде: `path/file.ts:88` — <причина>; происхождение: diff `<base>..<head>` добавил `:88` |
| `F-2` | <суть находки> | FAIL | легаси | Воспроизведено на <стенд> <дата>: <результат>; В коде: `path/file.ts:12` в main `<sha>` — та же строка; На проде <дата>: воспроизводится |

## Предположения

Всё, что не опирается на требование, код или прогон, — здесь и только здесь:

- Предположение: <что предполагаю> — <что нужно, чтобы его закрыть>.

## Разбор

Дальше — обычная проза: причины, механизмы, ссылки на код, скриншоты, логи.
Проза вердиктом не является: любой вывод, который должен что-то решать,
обязан стоять строкой в таблице выше.
