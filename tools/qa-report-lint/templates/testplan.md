# Тест-план: <тема> (<сервис>, <тикет / PR / ветка>)

Источник требований: <тикет / PR / спека / «письменного требования нет — критерий выведен из кода»>.
Ветка/SHA: <сервис> `<ветка>` @ `<sha>`. База для «ветка или легаси»: main `<sha merge-base>` / прод `<release-N>`.
Связанные файлы: баги — `BUGS-<тема>.md` (только открытые), прогресс — `PROGRESS-<тема>.md`, отчёт — `QA-REPORT-<тема>.md`.

План читают разработчики: источник кейса пишется словами («Требование: …», «В коде: `path:line`»,
«Предположение: …»). Буквами — только со строкой «Обозначения: [T] — требование, [C] — место в коде,
[R] — проверено прогоном на стенде, [A] — предположение, [?] — не проверено». Если результаты ведутся
в плане и у FAIL стоит метка происхождения — в шапке строка «Происхождение: ветка — дефект внесён
проверяемой веткой, на main и проде его нет; легаси — дефект есть и без ветки, на main или проде;
легаси+ветка — старая причина, которую ветка проявила или усилила».

## Контекст проверки

Блок из скила `stand-topology` — тот же, что выведен в чат до плана.

```
Контекст проверки
- Сервис/ветка → контур: <сервис> `<ветка>` → <стенд> (мой / общий) · образ на стенде = <tag/SHA>
- Локали и домены: все / только EN / … → домены: …
- Регион и запись: центр / регион; пишет ли код в БД
- Зависимости контура: общие для всех стендов сервисы, раздача сборки с CDN, …
- env: `env-diff` → новых переменных нет / N новых: …
```

## Кейсы

| ID | Что проверяем | Источник | Тип | Контур / локали | Ожидание | Способ |
| --- | --- | --- | --- | --- | --- | --- |
| `c1` | <сценарий> | Требование: <пункт требования> | позитив | <стенд>, <локали> | <что должно быть> | <инструмент: браузер / curl / MCP CMS / Playwright / логи …> |
| `c2` | <сценарий> | В коде: `path/file.ts:88` | негатив | … | … | … |
| `c3` | <сценарий> | Предположение: ожидание сформулировал я — <почему так> | граница | … | … | … |
| `c4` | тот же сценарий на базе | В коде: diff `<base>..<head>` | baseline | прод / стенд с main | на базе дефекта нет / есть | … |

Тип: позитив · негатив · граница · регресс · baseline. ID кейсов = Check ID в отчёте.
Кейс, появившийся в ходе прогона, дописывается с пометкой «(добавлен в ходе)». Кейс из плана не
удаляется: ненужный или недоступный получает в отчёте `N/A` / `NOT_VERIFIED` / `BLOCKED` с причиной.
