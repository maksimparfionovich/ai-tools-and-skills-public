# env-diff

Отвечает на вопрос перед прогоном ветки на стенде: **какие переменные окружения ждёт код этой ветки
и каких из них нет в gitops выбранного стенда или прода.** Главный сценарий — ветка добавила
переменную, никто не положил её в gitops, и сервис на стенде тихо работает не так или не стартует.

```bash
python3 tools/env-diff/env_diff.py --service backend --stand qa1
python3 tools/env-diff/env_diff.py --service frontend --stand prod --ref origin/feat/new-search
python3 tools/env-diff/env_diff.py --service prices --stand qa2 --all      # все непокрытые, не только новые
python3 tools/env-diff/env_diff.py --service backend --stand qa1 --json
python3 tools/env-diff/env_diff.py --list                                  # сервисы и контуры из настроек
```

Python 3.8+ и PyYAML (`python3 -m pip install pyyaml`), плюс `git`. Сетевых запросов нет. На Windows —
`python` вместо `python3`.

## Что делает

1. **Код** читается через `git grep` по дереву `--ref` (по умолчанию `HEAD` рабочей копии) —
   переключать ветки не нужно. Имена переменных извлекаются по шаблонам стека сервиса: `process.env.X`
   и хелперы с литералами у TS, `os.Getenv` и хелперы у Go, `runtimeConfig` + `process.env` у Nuxt,
   `VITE_*` у Vite, `config.get('X')` у Nest. Тесты исключены.
2. **База** — `--base` (по умолчанию `origin/main` или `origin/master`). «Новое в ветке» = имена, которых
   нет в базе.
3. **Gitops** — по стенду выбирается репозиторий, находится файл кластера и ApplicationSet приложения,
   разворачивается цепочка `valueFiles` (`$values/…` с подстановкой переменной стенда и, если есть,
   базы региона), собираются ключи `env:`, имена `envRaw`, список секретов (`secrets.vaultSecrets`) и
   env, зашитый в сам шаблон ApplicationSet.
4. **Дифф** и подсказка «куда добавлять»: файл стенда или общий values-файл; для репозитория с
   регионами — центр, регион или все сразу.

## Как читать вывод

| Строка | Значение |
| --- | --- |
| `НЕТ в gitops, default НЕТ → блокер` | ветка читает переменную без запасного значения, а на стенде её нет. Перед прогоном — завести в gitops или подтвердить, что она приходит из секрета |
| `НЕТ в gitops, default в коде есть` | сервис поднимется на значении по умолчанию; проверить, что оно устраивает стенд |
| `[похоже на секрет]` | имя вида `*_SECRET/TOKEN/KEY/DSN/DATABASE_URL`: ключи секретов в git не видны, скорее всего значение там |
| `В gitops, но код по ref не читает` | кандидаты в мёртвые переменные или имена, которые читаются не по шаблону |

Коды выхода: `0` — новых непокрытых нет; `1` — есть, но у всех есть default; `2` — есть блокер;
`3` — нет PyYAML или настроек.

## Настройка

`config.local.json` рядом со скриптом (пример — `config.example.json`), файл из `ENV_DIFF_CONFIG` или
`--config <файл>`.

| Поле | Что задаёт |
| --- | --- |
| `repos_root` | Папка с клонами сервисов и gitops-репозиториев (`~` раскрывается; относительный путь — от корня проекта) |
| `services.<имя>` | `repo` (путь от `repos_root`), `gitops_apps` (имена приложений в gitops), `kind` (`ts`, `nuxt`, `go`, `vite`, `nest`, `ts+go`), `paths` (pathspec для `git grep`, с `:(exclude)…`), `go_paths` (для `ts+go`), `dynamic_literals` (хелперы вида `env('NAME', default)`), `ignore`, `note` |
| `gitops.<ключ>` | `path`, `label` (как называть в подсказках), `kind` (`stands` — стенды; `regional` — центр и регионы), `stands` (имена стендов), `aliases` (как называют контур в разговоре → значение переменной стенда), `center` (для `regional`), `common_hint`, `secrets_hint`, `layout` (переопределение раскладки для этого репозитория) |
| `layout` | Раскладка gitops (ниже) |
| `platform_vars` | Переменные, которые даёт платформа, а не gitops: их в диффе не показывать |

**Раскладка gitops** (`layout`), значения по умолчанию:

| Поле | По умолчанию | Что это |
| --- | --- | --- |
| `apps_dir` | `apps` | Папка приложений: `<apps_dir>/<app>/env.yml`, `<apps_dir>/<app>/<стенд>/value.yml` |
| `clusters_glob` | `clusters/**/*.yml` | Файлы кластеров: в каждом — имя стенда и ключи включения приложений |
| `appsets_glob` | `appset/**/*.yml` | Шаблоны ApplicationSet |
| `stand_var` | `stand_code` | Ключ имени стенда в файле кластера и переменная `{{ .stand_code }}` в шаблоне |
| `stand_alt_key` | пусто | Запасной ключ имени стенда в файле кластера |
| `franchise_var` | пусто | Переменная базы региона в шаблоне; пусто — регионов нет |
| `enable_suffix` | `-enabled` | Ключ включения: `<app>[-api\|-worker]<suffix>: true` |
| `app_variants` | `["-api", "-worker"]` | Суффиксы вариантов приложения |
| `common_values` | `env.yml` | Общий values-файл приложения |
| `stand_values` | `value.yml` | Values-файл стенда |

Раскладка рассчитана на ArgoCD ApplicationSet с multi-source `$values`. Если у вас другая схема
(Kustomize, Helmfile), извлечение из кода работает как есть, а функцию `read_gitops` придётся
адаптировать.

## Чего скрипт не знает

- **Ключи внутри секретов.** В git только имя секрета и путь. Переменная может быть «не в gitops» и при
  этом приходить из секрета — для `*_SECRET`/`*_KEY`/`DSN` это норма; проверять в хранилище секретов
  или `kubectl get secret -o jsonpath` на стенде.
- **Default — эвристика.** TS: `??`/`||` в той же строке или второй аргумент хелпера; Go: любой хелпер,
  кроме `os.Getenv`/`mustEnv`/`required`. Флаги вида `os.Getenv("X") != "true"` считаются «без
  default». Многострочные выражения не видны.
- **Nuxt:** производные `NUXT_[PUBLIC_]<SNAKE>` от ключей `runtimeConfig` считаются «с default» (значение
  есть в самом объекте). Имя из `process.env` может не совпадать с автоименем ключа.
- **Воркеры** — отдельные приложения gitops со своими values: `--app <имя>`.
- Gitops-репозитории читаются из рабочей копии — перед прогоном `git pull`; дата их HEAD печатается в
  шапке.

## Добавить сервис

Запись в `services`: путь репозитория, имена приложений gitops, тип извлечения, pathspec для
`git grep`, при необходимости `dynamic_literals`, `ignore`, `note`. Проверка — прогнать с `--all` и
глазами сверить список с `.env.example` репозитория.
