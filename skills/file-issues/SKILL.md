# Заведение задач GitHub

Задача — действие наружу: её видит команда. Поэтому порядок жёсткий: собрать → проверить → показать
список → «да» пользователя → завести → сверить. Механика — скрипт `tools/gh-issues/gh_issues.py`
(README рядом с ним), факты проекта — организация, доска, люди, шкала приоритета, куда что заводить —
в `local.md` рядом с этим файлом (пример — `local.example.md`). Прочитай `local.md` перед первой
задачей в сессии.

## У каждой задачи обязательно

| Что | Правило |
| --- | --- |
| Репозиторий | Где будут править код (`local.md`, «Куда заводить»). Не там, где заметили, а там, где исполнят |
| Заголовок | По-английски, с префиксом `[сервис]`: `[payload-back] Login form hides the lock reason` |
| Текст | По-русски: что происходит → почему (место в коде `path:line` + ветка/SHA) → чем грозит → что предлагаю → происхождение → где воспроизведено (стенд и дата). Основания и происхождение — **словами**, без голых `[R]`/`[C]`/`ветка`/`легаси` (корневой `CLAUDE.md`, раздел 9) |
| Исполнитель | **Всегда.** Ниже — как выбрать |
| Приоритет | **Всегда.** Поле организации `Priority`, не метка; шкала — в `local.md` |
| Доска | Карточка на доске проекта, статус по умолчанию — из настроек скрипта |
| Метки | Только существующие в репозитории (`bug` для дефекта). Новые метки не создавать |

### Исполнитель

1. Дефект найден в PR или ветке → **автор PR/ветки**: `gh pr view <N> -R <org>/<repo> --json author`,
   для ветки без PR — автор коммитов ветки (`git log --format='%an %ae' origin/main..<ветка>`), логин —
   по таблице людей в `local.md`.
2. Легаси без ветки → владелец направления по таблице «репозиторий → исполнитель» в `local.md`.
3. В таблице нет или сомнение → не угадывать: оставить вопрос в списке на подтверждение.

Назначать можно только тех, кого скрипт пропускает проверкой (`assignable`). Ботов (`@copilot`) не назначать.

### Приоритет

Предлагаю я по шкале из `local.md`, решает пользователь в списке. Сомневаешься между двумя — предложи
выше и скажи почему.

## Порядок

1. **Собрать задачи в файл** `ISSUES-<тема>.md` в корне workspace (формат — README скрипта): раздел
   `## N. [сервис] Заголовок`, под ним строка `Репо: … · Исполнитель: @login · Приоритет: … · Метки: …`,
   дальше текст. Одна задача — один раздел. Если задачи уже лежат в `BUGS-*`/отчёте — переносить текст,
   не переписывая выводы.
2. **Проверить, что задача ещё нужна:** ветка могла уйти вперёд после прогона — `git log
   <SHA прогона>..origin/<ветка>` и `git show` по месту причины. Починено → задачу не заводить, сказать.
3. **План скрипта** (только чтение GitHub):
   ```bash
   python tools/gh-issues/gh_issues.py ISSUES-<тема>.md
   ```
   Ловит: нет исполнителя или приоритета, исполнителя нельзя назначить, нет метки или варианта
   приоритета, дубль заголовка, голые маркеры. Ошибки — править файл, не обходить флагами.
   Похожие задачи с другим заголовком скрипт не видит — поискать самому: `gh issue list -R <repo>
   --state all --search "<ключевые слова>"`.
4. **Показать пользователю список**: репозиторий, заголовок, исполнитель, приоритет, метки, статус на
   доске — и ждать явного «да» на этот список. Правки пользователя → в файл → снова план.
5. **Завести:** тот же вызов с `--apply`. Скрипт создаёт по одной, сразу вписывает `Задача: <ссылка>`
   в раздел, ставит приоритет и карточку и сверяет. Строка `✗` — что-то не записалось: дописать через
   `set`, не создавать задачу заново.
6. **Итог пользователю:** ссылки, исполнитель, приоритет, статус — из вывода сверки, не из плана. Если
   задачи пришли из `BUGS-*` или отчёта — вписать туда ссылки (это та же операция).

### Уже заведённые задачи

Нет приоритета или исполнителя у существующей задачи:

```bash
python tools/gh-issues/gh_issues.py set <org>/<repo>#<N> --priority <вариант> [--assignee <login>]
```

Без `--apply` — план (сейчас → станет); с `--apply` — запись после «да». Чужие задачи — только по
прямой просьбе пользователя.

## Нельзя

- Заводить, править, закрывать задачи, ставить карточки и комментировать без «да» пользователя на
  конкретный список. Одно «да» покрывает показанный список, не следующий.
- Менять настройки доски, поля организации, метки репозиториев, workflow — это решает команда.
- Обходить проверки скрипта (`--allow-duplicate` — только если пользователь сам сказал, что это не дубль).
- Писать в задачу секреты, токены, пароли тестовых учёток, персональные данные сверх нужного для
  воспроизведения.

## Ловушки

- `gh` не находится (сессия запущена до установки) — скрипт ищет `C:\Program Files\GitHub CLI\gh.exe`
  сам; для ручных команд — полный путь или перезапуск приложения.
- Кириллица в `--body` на Windows ломается — текст только файлом (`--body-file`), скрипт так и делает.
- Колонка Priority на доске — зеркало поля организации; `gh project item-edit` её не заполнит, только
  мутация `setIssueFieldValue` (скрипт) или вручную в задаче.
- Доска может сама ставить статус новой карточке — скрипт его не затирает.
- Поиск дублей GitHub работает по словам: близкий по смыслу дубль с другими словами не найдётся.
