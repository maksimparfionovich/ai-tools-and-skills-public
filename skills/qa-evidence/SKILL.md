# Обоснование вердиктов в QA

Короткая версия правил для `CLAUDE.md` проекта — `docs/claude-md-rules.md` в репозитории, откуда
взят скил. Здесь механика и пограничные случаи. Формат, правила линтера и шаблоны —
`tools/qa-report-lint/README.md`, `tools/qa-report-lint/templates/testplan.md` и
`tools/qa-report-lint/templates/qa-report.md`.

Порядок любого тестирования: **контекст контура** (`stand-topology`) → **тест-план** (раздел ниже) →
выжимка плана в чат → прогон → отчёт, где каждый кейс плана получил вердикт.

## Буквы — для нас, для разработчика — слова

`[R]`, `[C]`, `[T]`, `[A]`, `[?]` — наша стенография. Отчёты, `BUGS-*` и тест-планы читают
разработчики, и голые буквы им ничего не говорят. Основание пишется в одном из двух видов:

- **словами** — подпись в начале фрагмента, с двоеточием:

| Вместо | Пишем | Пример |
| --- | --- | --- |
| `[R]` | Воспроизведено / Проверено / Не воспроизводится на `<стенд>` `<дата>`: | «Воспроизведено на qa2 13.10: колонка пустая» |
| `[C]` | В коде: / Причина в коде: | «В коде: `src/collections/Articles.ts:88` — поле без `index`» |
| `[T]` | Требование: / По тикету: | «Требование: AC-2 SHOP-101» |
| `[A]` | Предположение: / Догадка: | «Догадка: CDN держит старую версию» |
| `[?]` | Не проверено: / Причина в коде не найдена: | «Не проверено: на qa2 нет платной статьи» |

  У подписи прогона стенд или дата обязательны: «Воспроизведено:» без них прогоном не считается.
- **буквами с расшифровкой** — строка в шапке файла: «Обозначения: [T] — требование, [C] — место в
  коде, [R] — проверено прогоном на стенде, [A] — предположение, [?] — не проверено».

Описание бага и строки «Статус» — всегда словами; буквы допустимы только в сводных таблицах и только
с расшифровкой. То же с метками происхождения `ветка`/`легаси`/`легаси+ветка` — раздел «Ветка или
легаси» ниже, линтер E16. Линтер засчитывает подписи словами как маркеры во всех правилах (E1–E4, E8, E9, E14,
W2) и валит буквы без расшифровки (E15). Дальше в этом скиле буквы — сокращение для нас; в файле
для разработчиков их заменяют подписи из таблицы выше.

## Главное правило эскалации

`NOT_VERIFIED` — **не разрешение остановиться, а команда пойти и добыть `[R]`.**

Порядок всегда такой:

1. Основание можно добыть доступными средствами → **добудь сам**, не спрашивай и не понижай вердикт.
2. Добыть нельзя → `NOT_VERIFIED`/`BLOCKED` **с названной причиной**, и в отчёт строкой: что
   именно нужно, чтобы закрыть (доступ, креды, согласие на общий стенд, деплой ветки).
3. Вопрос пользователю — только когда без его решения проверка невозможна (общий стенд, прод,
   выбор контура). Один вопрос на всё недостающее, а не по одному на каждый пункт.

Понижение вердикта вместо доступной проверки — такой же дефект, как и выдуманный `PASS`.

## Чем добывается `[R]`

| Что проверяем | Инструмент |
| --- | --- |
| UI, DOM, метатеги, рендер | браузер под управлением агента (Playwright, agent-browser, встроенный браузер); браузер с залогиненной сессией — где нужна авторизация |
| Поведение бэкенда, коды ответов | `curl` или `fetch` изнутри пода, REST/GraphQL стенда |
| Логи пода, 500, «почему висит» | скил `stand-logs` (`lokilogs`) |
| Тестовые данные, публикация, локали | MCP CMS (`tools/payload-cms-mcp`) |
| Регресс, red→green | автотесты проекта |
| Контракт, схемы, селекторы | код сервиса — это `[C]`, не `[R]` |
| Состояние стенда, CI | `kubectl get pods`, `gh run list/view` |
| Разовая операция над БД/индексом | скил `run-db-script` |

Свои стенды — в карте скила `stand-topology` (`local.md`): на них проверяю без спроса. Остальные
общие, прод — только по явному согласию.

## Перед планом проверок — контекст контура (скил `stand-topology`)

До того как расписывать проверки, пройти чеклист скила `stand-topology` и вывести блок «Контекст
проверки»: контур и сборка на нём, затронутые локали и домены, центр или регион прода и нужна ли
запись в БД, зависимости контура, и результат `tools/env-diff` — новые переменные ветки, которых нет
в gitops. Карта хостов и регионов — там же; здесь её не дублировать.

## Тест-план — первый шаг любого тестирования

Любое тестирование начинается с тест-плана: проверка фичи, ретест, приёмка ветки, PR или тикета,
проверка релиза, аудит поведения на контуре. План пишется **до первого прогона**, сразу после блока
«Контекст проверки». Не нужен он только там, где прогона не будет: «сверь код», вопрос по коду —
такой отчёт пишет `Тест-план: N/A — <почему>`.

**Форма — по размеру задачи, но план есть всегда.**

- Тикет, PR, ветка, релиз, ретест из нескольких кейсов → файл `TESTPLAN-<тема>.md` в корне проекта
  по шаблону `tools/qa-report-lint/templates/testplan.md`. К нему на ту же тему два файла, в шапке
  каждого — ссылки на остальные:
  - `BUGS-<тема>.md` — **только открытые дефекты**: воспроизведение, доказательства, влияние,
    предлагаемый фикс. Ни хронологии, ни снятых находок: файл уходит авторам ветки как рабочий документ;
  - `PROGRESS-<тема>.md` — статус по контурам, хронология, снятые находки с причиной снятия,
    договорённости, следующие шаги. Снятый дефект переезжает из `BUGS-*` сюда.
- Разовая проверка (один вопрос, 1–3 кейса) → раздел `## Тест-план` в самом отчёте; если файла-отчёта
  не будет — тот же план коротко в чате до прогона.

**Минимальный состав плана:**

1. Шапка: что тестируем (сервис, ветка @ SHA, тикет/PR), источник требований, база для «ветка или
   легаси» (main `<merge-base>` / прод `<release-N>`).
2. Блок «Контекст проверки» из `stand-topology` — тот же, что выведен в чат, с пунктом `- env: …`
   (результат `env-diff` или `N/A — почему`).
3. Таблица кейсов `ID | Что проверяем | Источник | Тип | Контур / локали | Ожидание | Способ`.
   Источник — «Требование: AC-N», «В коде: `path:line`» или «Предположение: ожидание сформулировал я»
   (буквами `[T]`/`[C]`/`[A]` — только с расшифровкой в шапке).
   Тип — позитив / негатив / граница / регресс / baseline. Способ — чем добываю `[R]` (таблица выше).
4. «Покрытие» — девять измерений, у каждого ID кейсов или `N/A — почему` (таблица ниже).
5. «Что нужно от пользователя» — один список на всё (общий стенд, прод, креды, решения) или «нет».

| Измерение | О чём не забыть |
| --- | --- |
| Требования | каждый пункт тикета, PR или спеки — хотя бы один кейс; требования нет — `[?]` + `[A]` |
| Изменения в коде | `git diff <база>..<ветка> --stat`: каждое изменённое поведение покрыто, в том числе то, чего нет в тикете |
| Негатив и границы | ошибки, пустые и неверные данные, права, повтор, отмена, гонки, лимиты |
| Локали и домены | по умолчанию все локали и домены из карты; RTL; домены, которых нет на стендах, — GET на проде |
| Регион и запись в БД | центр или регион прода; пишет ли код в БД (если у регионов база только на чтение) |
| Окружение | `env-diff`, зависимости контура: сервисы, общие для всех стендов, раздача сборки с CDN |
| База (ветка или легаси) | baseline на main или проде — для происхождения багов и `FAIL_EXPECTED` |
| Регресс и автотесты | что рядом может сломаться; какие автотесты прогнать, нужен ли новый |
| Интерфейс: desktop / mobile | если затронут UI — обе раскладки; без UI — `N/A` |

`N/A` — честный ответ, если причина названа: «фронт только читает, записи в БД нет». Пустое
измерение или `N/A` без причины — дефект плана (линтер E12).

**В чат — выжимка плана:** сколько кейсов, что ушло в `N/A` и почему, что нужно от пользователя.
Ждать ответа — только если без решения пользователя прогон невозможен (общий стенд, прод, креды);
иначе прогон начинается сразу, пользователь поправит по ходу.

**План живой, но не теряет кейсы.** Кейс, появившийся в ходе прогона, дописывается в план с пометкой
«(добавлен в ходе)». Кейс из плана не удаляется: ненужный или недоступный получает в отчёте `N/A`,
`NOT_VERIFIED` или `BLOCKED` с причиной.

**Связь с отчётом.** В шапке отчёта — `Тест-план: TESTPLAN-<тема>.md`. ID кейсов плана = Check ID в
таблице проверок; каждый кейс получает вердикт — строкой в отчёте или колонкой результата в самом плане.

**Линтер** (`tools/qa-report-lint`, хук на запись отчёта): E10 — отчёт без тест-плана; E11 — кейс
плана без вердикта; E12 — в «Покрытии» нет измерения или у него нет ни кейса, ни `N/A` с причиной;
E13 — нет блока «Контекст проверки» или в нём нет пункта `env`; E14 — нет таблицы кейсов или у кейса
нет источника.

## Пограничные случаи

**Чтение кода никогда не даёт `PASS` по поведению.** `[C]` обосновывает только утверждения о
коде («хук отсутствует», «порядок аргументов обратный»). Утверждение о том, что видит
пользователь, требует `[R]`. Формулировка для непроверенного: «по коду ожидается X, на контуре
не проверено» + `NOT_VERIFIED`.

**Требования нет.** Бывает часто. Тогда прямо: `[?] письменного требования нет — критерий
выведен из кода` или `[A] ожидание сформулировал я`. Молча выдать своё ожидание за требование
тикета — худшая из ошибок этого класса, потому что она не видна на ревью.

**«PASS в пределах доступного»** — это `PARTIAL`, а не `PASS`. Линтер это ловит (W1).

**Baseline «до фикса»** помечается `FAIL_EXPECTED`: красный прогон на базовом SHA — это
доказательство, а не дефект, и итоговому `PASS` он не противоречит.

**Прод как референс.** Если эталон поведения — прод (данные стендов отстают), сравнение со стендом
без сверки с продом — `[A]`, не `[R]`.

**Дефект найден мимоходом, не проверен.** Не пиши его вердиктом. `[A]` + «не проверял» — или
проверь. Третьего нет.

## Причина бага — из кода

Мало увидеть дефект — надо понимать, **откуда в коде он следует**. Поэтому:

- **У каждого `FAIL` есть `[C]` `path:line`** того места в коде или конфиге, из которого вытекает
  дефект: код сервиса, библиотека в `node_modules/`, gitops-yaml. Если найти не
  удалось — **оба маркера сразу**: `[?] причина в коде не найдена, потому что …` (явное
  обозначение) и `[A] догадка: …`. Одна догадка без явного «не найдена» выглядит как объяснение и
  останавливает поиск; одно «не найдена» без догадки не даёт, от чего оттолкнуться. Как и для
  `NOT_VERIFIED`, «не найдена» — команда копать дальше, а не разрешение остановиться. Линтер: E8.
- **Утверждение о причине требует основания.** «Поведение Payload», «баг библиотеки», «причина —
  …» — это `[C]` со ссылкой на код библиотеки, иначе `[A]`. «Не из этого PR», «есть и без фикса» —
  это `[R]` прогона на сборке без фикса (baseline) или `[C]` по diff, иначе `[A]`. Линтер: W2.
- **Плавающий дефект — найди способ надёжно его воспроизвести.** Механизм гонки доказывает не
  «1 из 3», а прогон, где исход задан искусственно. Способ, который работает в админке Payload:
  в странице обернуть `window.fetch` и задержать нужный запрос (например, `form-state` или
  `where[id][in]`). Так проверяется и механизм, и то, есть ли дефект на baseline. Это инструмент
  отладки, код стенда он не меняет. **В вердикте дефект остаётся плавающим**: пиши «плавающий,
  надёжно воспроизводится задержкой …», а не «стабильный» или «детерминированный» — у
  пользователя без задержки он проявляется не всегда.
- **Находка — строкой в таблице.** Каждая `F-N`/`BUG-N` — строка «ID | суть | вердикт |
  основание»; проза под таблицей только поясняет. Находку, описанную только прозой, линтер не видит
  (E7).

## Ветка или легаси — у каждого бага

Кроме причины в коде, про каждый `FAIL` сразу отвечаем: **внесла его проверяемая ветка или он был
и без неё.** Это часть причины, а не отдельный этап: нашёл `[C]` место причины — тут же сравни его с
базой. Линтер: E9.

**База** — то, во что вливается ветка: `git merge-base origin/main origin/<ветка>` (обычно совпадает
со свежим `origin/main`). Для поведения, которое видит пользователь, удобная база — прод (проверка
только на чтение). Если на main дефект есть, а на проде нет (его внёс другой, ещё не выкаченный PR), —
это всё равно `легаси` относительно проверяемой ветки; назови PR, который его внёс.

**Значения.** В таблице находок — колонка «Происхождение», в таблице проверок — `Происхождение: … —
см. F-n`. Основание пишется в ячейке «Основание» рядом с причиной.

| Значение | Когда | Основание |
| --- | --- | --- |
| `ветка` | на базе дефекта нет | `[C]` diff `<base>..<head>` по месту причины — строка появилась или изменилась в ветке; или `[R]` baseline на базе — дефекта нет |
| `легаси` | дефект есть и без ветки | `[R]` baseline на проде / стенде с main — воспроизводится; или `[C]` `path:line` в main `<sha>` — та же причина **и** тот же путь к ней |
| `легаси+ветка` | причина старая, но ветка её проявила (сделала достижимой) или усилила последствия | оба: `[C]` причина в main `<sha>` + что поменяла ветка (diff) |
| `не установлено` | сравнить с базой не удалось | `[?]` почему (стенд с main занят, нет данных…) + `[A]` догадка. Как и `NOT_VERIFIED`, это команда копать дальше |

**Метка — для нас, разработчику — расшифровка.** `ветка`, `легаси`,
`легаси+ветка` — та же стенография, что и `[R]`: из голой метки разработчик не поймёт, держит ли баг
ветку. В файле для разработчиков — одно из трёх:

- строка расшифровки в шапке: «Происхождение: ветка — дефект внесён проверяемой веткой, на main и проде
  его нет; легаси — дефект есть и без ветки, на main или проде; легаси+ветка — старая причина, которую
  ветка проявила или усилила» (или таблица `| легаси | <что значит> |`);
- метка с пояснением в той же строке: «легаси — есть и без ветки: на проде 13.10 воспроизводится»,
  «легаси (есть и без ветки)»;
- сразу словами, без метки: «внесён веткой», «есть и без ветки», «старая причина, ветка проявила».

В описании бага (`BUGS-*`, разделы «Разбор») происхождение — всегда словами или меткой с пояснением.
Голая метка у `FAIL` без расшифровки в файле — линтер E16.

**Как установить.** Всё это — чтение в клоне репозитория, без `checkout`:

```bash
base=$(git merge-base origin/main origin/<ветка>)
git diff "$base" origin/<ветка> -- <path>                 # тронула ли ветка место причины
git show "$base":<path> | sed -n '<from>,<to>p'           # как это место выглядит на базе
git log --oneline "$base"..origin/<ветка> -- <path>       # какие коммиты ветки его меняли
git blame -L <line>,<line> origin/<ветка> -- <path>       # каким коммитом пришла строка
```

**Ловушка: «та же строка в main» ≠ легаси.** Если ветка не трогала место причины, но поменяла путь к
нему (новый вызов, другие данные, снятая защита выше по стеку), на базе дефект не проявляется — это
`легаси+ветка`, а не `легаси`. Сверки одной строки поэтому мало: проследи путь от входа до причины в
обеих версиях. Где дешёвый baseline-`[R]` доступен (прод на чтение, мой стенд с main), — сделай его:
он сильнее `[C]`.

**Отчёт без проверяемой ветки** (аудит прода, разбор прод-инцидента) — правило то же. `ветка` =
дефект внесён конкретным недавним релизом или PR, и его надо назвать (`release-N`, PR #N; `git log
<пред. релиз>..<релиз> -- <path>`, `git blame`, версия прода — эндпоинт версии, если он есть).
`легаси` — дефект старше: blame указывает на давний коммит, дефект был и в прошлых релизах.

**Зачем.** От происхождения зависит решение по ветке: `ветка` обычно держит мерж или выкатку и
чинится в ней; `легаси` — отдельная задача владельцам сервиса, не повод держать ветку; `легаси+ветка`
— вопрос, чинить ли старое место в ветке или откатить то, что его проявило.

## Дефект, найденный автоматизацией UI

Если «сломано» показала только моя автоматизация (синтетические события, программная прокрутка,
клики по координатам со скрина) — сначала **подтверди вторым способом**: руками или
пользователем, другим методом ввода, чтением обработчика в коде. До этого — `[A]`, не `FAIL`.

Прецедент (находка снята): «фильтр списка в админке грузит только 20 вариантов» оказался
артефактом. react-select подгружает следующую страницу, когда колесо «доезжает до низа», и держит
флажок «уже внизу», который сбрасывается только колесом, пока до низа есть место. Автоматизация
прыгала `scrollTop` сразу в конец — флажок не сбрасывался. Код пагинации при этом был корректен.
Правильная эмуляция — прокрутка колесом небольшими шагами.

## Вывод в чат

Файл — источник истины, чат — выжимка. Но и в чате любой вердикт несёт основание: одна строка
`PASS/FAIL/...` + `[T]/[C]/[R]/[A]/[?]`, а у `FAIL` — ещё и происхождение (`ветка` / `легаси` /
`легаси+ветка` / `не установлено`). Развёрнутая проза в чате — пояснение, не вердикт. Буквы в чате с
пользователем допустимы — он их знает; текст, который он перешлёт разработчикам (сообщение, комментарий
в PR), пишется словами.
