# Запуск Payload-скрипта на базе стенда

Разовые сервисные скрипты Payload (`src/scripts/*.ts`) исполняются командой `pnpm payload run
<script>` **внутри пода бэкенда** — процесс наследует его окружение (`DATABASE_URL`, `OPENSEARCH*` и
т. д.). Канонический пример — реиндекс поиска (`src/scripts/reindex-search.ts`: читает Postgres,
пишет в OpenSearch), но механика одна для любого такого скрипта. Задача скила — попасть в нужный
под нужного стенда, при необходимости увести чтение на реплику и проверить результат.

Факты проекта — как называются namespace стендов, как выглядит имя пода, какой командой открывается
доступ к кластеру, где эндпоинт для проверки — в `local.md` рядом с этим файлом (пример —
`local.example.md`). Прочитай его перед запуском.

## Предусловия (проверить, не предполагать)

1. **Стенд назван.** Если нет — спросить. Прод — не этот скил (ниже).
2. **Какой скрипт и что он делает**: только читает? пишет во внешнюю систему? меняет базу? От этого
   зависит, нужна ли реплика и насколько операция обратима. Прочитать скрипт в репозитории бэкенда.
3. **Стенд общий** — запускать только после явного согласия пользователя или по прямой команде с
   названным стендом. Наличие прав на стенд — не разрешение действовать. Свои стенды перечислены в
   `local.md`.
4. **Доступ к кластеру есть** (живая сессия, `kubectl` видит namespace). Нет — сказать, чего не
   хватает, и остановиться; не искать обходных путей.

## Стенд — `kubectl exec` по имени пода

Вход двухшаговый: сперва имя живого пода, затем `exec` по имени (не по `deploy/…`: права часто
выданы только на `pods get/logs/exec`, и минимальный скоуп — хорошая дисциплина).

```bash
kubectl get pods -n <стенд>
# найти Ready-под бэкенда: статус Running, READY N/N, свежий ReplicaSet
kubectl exec -n <стенд> <имя-пода> -- \
  sh -c 'nohup env DB_POOL_MAX=50 pnpm payload run src/scripts/reindex-search.ts > /tmp/reindex.log 2>&1 & sleep 1; tail -n 20 /tmp/reindex.log'
```

- `nohup … &` — долгий прогон переживает обрыв сессии; прогресс — `kubectl exec … -- tail -n 50 /tmp/reindex.log`.
  Это `/tmp` пода: при рестарте пода лог пропадёт, поэтому прогресс мерить ещё и по результату.
- `DB_POOL_MAX=50` — ускорение **только для стенда** (база простаивает). На прод не переносить.
- Команда доступа к кластеру может отличаться (`tsh kubectl`, свой `--context`) — см. `local.md`.
- В Git Bash на Windows пути внутри пода (`/tmp/...`) портятся: `MSYS_NO_PATHCONV=1` перед командой.

## Реплика или primary — через `DATABASE_URL`

Ни `kubectl exec`, ни веб-терминал сами базу не выбирают: процесс наследует `DATABASE_URL` пода, а он
обычно указывает на **primary**. Куда пойдёт прогон, решает то, что делает скрипт:

- **Скрипт только читает базу** (реиндекс: читает статьи, пишет в OpenSearch) — можно увести на
  **реплику**, чтобы не грузить primary. У CloudNativePG read-only сервис отличается суффиксом
  `-ro` вместо `-rw`:
  ```bash
  DATABASE_URL=$(printf '%s' "$DATABASE_URL" | sed 's/-rw/-ro/') pnpm payload run src/scripts/<скрипт>.ts
  ```
  Перед прогоном проверить, что подмена попала в host, не печатая кредов:
  `sh -c 'printf "%s" "$DATABASE_URL" | sed "s/-rw/-ro/" | sed "s#//.*@#//***@#"'`. Если `-rw` в host не
  нашлось — остановиться и разобраться.
- **Скрипту нужно писать в базу** — только primary (реплика запись не примет): без подмены.
- То же для OpenSearch: путь записи — только на записываемый endpoint; на read-реплику — только чтение.

На стенде обычно хватает primary. Различие важно на проде — там решает человек.

## Прод — не запускать, а подготовить

Скил на проде ничего не исполняет: ни `exec`, ни Job. Если просят «прогнать на проде» — подготовить
для человека точные команды (вход в под по имени, подмену `-rw`→`-ro` для читающего скрипта, k8s Job
для долгого прогона), напомнить про штатный пул (без `DB_POOL_MAX`) и про дельта-прогон вместо
полного (боевой индекс уже живой), и отдать пользователю. Kubeconfig с долгоживущим токеном — секрет:
не печатать, не класть в git и синхронизируемые папки.

## Проверка результата снаружи

- **Эндпоинт стенда** (GraphQL или REST): метрика до и после. Для реиндекса — число найденных
  документов по запросу (`totalDocs`). WAF часть клиентов режет по User-Agent (`Python-urllib` → 403):
  слать браузерный UA. Для локалей с иероглифами и арабским латинский запрос почти ничего не найдёт —
  брать слово на языке локали.
- **Прогресс — по результату, а не по логам пода:** stdout процесса из `exec` в Loki не попадает. Логи
  самого пода — скил `stand-logs`.
- Эталон в базе — read-only доступ к Postgres стенда, если он есть (см. `local.md`).

## Грабли

- Foreground `exec` умирает на обрыве сессии → `nohup` в фоне.
- Перед повтором проверь по коду, идемпотентен ли скрипт: реиндекс, написанный как upsert с чисткой
  лишнего по локали, можно гнать повторно, и поиск во время прогона не гаснет. Создание индекса «если
  его нет» маппинг **не мигрирует**: при смене маппинга — сначала удалить индекс или писать в новый и
  переключить алиас.
- После заливки базы на стенд поды бэкенда не переподключают пул → нужен рестарт (перевыкатка), это
  отдельно от скрипта.

## Происхождение

Скил написан коллегой. У нас: прод-часть выключена — скил только готовит команды для человека;
основной вход — `kubectl exec` по имени пода через личную сессию (веб-терминал ArgoCD — запасной
путь, в него команды вставляет человек); правило общих стендов — только с согласия.
