# Выкатка ветки на стенд (теги)

Механика для сервисов, у которых CI выбирает стенд по словам в имени тега: **пуш тега → сборка в CI
→ стенд выбирается по слову в теге → CD выкатывает**. Скрипт `scripts/stand_tag.py` строит тег,
прогоняет его через ту же логику, что CI репозитория (правила описаны в `scripts/config.local.json`),
и пушит, только если CI выкатит ровно на один нужный стенд. Рабочую копию и ветки не трогает
(`git push origin <sha>:refs/tags/<тег>`), так что грязная копия не мешает. Пуш — по SSH-ключу
пользователя; токен GitHub не нужен.

Факты проекта — какой кластер, как смотреть поды, что особенного у отдельных репозиториев — в
`local.md` рядом с этим файлом (пример — `local.example.md`). Прочитай его перед первой выкаткой в
сессии.

## Запрет прода

- **Прод и UAT катит только человек.** Любая просьба «на прод / UAT / релиз» — отказ с объяснением.
- Только пуш **одного** тега. Ручной запуск сборки (`workflow_dispatch`) скил не использует вообще:
  там обычно можно выбрать прод.
- В теге не бывает релизной подстроки (`release_substring`, по умолчанию `release` — CI многих
  сервисов ищет её где угодно в имени и катит прод), `prod`, `uat`. Не `git push --tags`, не трогать
  существующие теги, не публиковать GitHub Release. В gitops-репозитории — только ветки и PR: в `main`
  не пушить и PR не мержить (там то, что выкатывается).
- Технически это держит PreToolUse-хук `tools/deploy-guard`. Если он заблокировал команду — **не
  обходить** (другой формулировкой, скриптом, API, браузером): сказать пользователю, что именно
  заблокировано и почему.

## Порядок

1. **Что катим:** репозиторий, ветка на origin, стенд. Не названо — спросить. Для репозитория с
   проектами (`kind: project`) ещё `--project <код>`. Список — `stand_tag.py --list`.
2. **Стенд:** свои (`own_stands` в настройках) — без спроса. Остальные общие: только если
   пользователь сам назвал этот стенд или согласился → `--shared-stand-ok`. Наличие прав ≠ разрешение.
3. **Контекст:** по чеклисту скила `stand-topology`. Если подключён `tools/env-diff` — прогнать его
   для ветки и стенда: новые переменные окружения, которых нет в gitops стенда, уронят под после
   выкатки — сказать об этом до пуша.
4. **План (dry-run):**
   ```bash
   python3 .claude/skills/deploy-to-stand/scripts/stand_tag.py --repo <repo> --branch <ветка> --stand <стенд>
   ```
   Печатает ветку и SHA, тег, ожидаемый тег образа, что сделает CI. Exit 0 — чисто, 2 — СТОП (ниже).
5. **Пуш:** тот же вызов + `--push`. Прямая просьба пользователя «выкати <ветку> на <стенд>» =
   согласие на пуш этого одного тега. Если ветку или стенд выбрал я сам — сначала показать план и
   спросить.
6. **Проверка** (ниже). Итог пользователю: тег, SHA, стенд, что под реально на этом образе.

На Windows вместо `python3` — `python`.

## Стопы (exit 2) и что делать

| Сообщение | Действие |
|---|---|
| имя ветки опасно: релизная подстрока, `prod`/`uat`, другой стенд, чужой код проекта, особые слова репозитория | спросить у пользователя короткую метку → `--label <метка>`; метка проходит те же проверки |
| общий стенд | спросить; после «да» → `--shared-stand-ok` |
| CI не выкатывает по тегу на этот стенд | сказать пользователю; у этого репозитория стенд по тегу недоступен |
| стоп из `stops` репозитория | прочитать причину вслух: обычно это делает человек или девопс |
| workflow в ветке ≠ default-ветке | показать `git diff` (команда в выводе); если разница не про выбор стенда и прод — `--accept-workflow-diff`, иначе спросить |
| раннер, которого больше нет / нет workflow в ветке | ветку надо подлить из default-ветки — отдельная операция, только с согласия |
| CI в default-ветке изменился (blob другой) | перечитать workflow репозитория, обновить его запись в `config.local.json` (`tag_tokens`, `blob`) и только потом катить |
| репозиторий из `excluded` | сказать, что скил его не катит, и почему |

Пуш упал: pre-push хук — спросить пользователя про `--no-verify`; SSH к GitHub режется — `--https`
(через Git Credential Manager или `gh auth`).

## Проверка после пуша

CI и CD обычно занимают 5–15 минут. Если статусов сборки не видно (нет `gh`), смотреть сам стенд —
команда доступа к кластеру в `local.md`, например:

```bash
kubectl get pods -n <стенд> -o custom-columns='NAME:.metadata.name,IMAGE:.spec.containers[*].image'
```

Успех = поды сервиса на образе `<тег>-<sha7>` и Ready. Хвост тега сверить с SHA из плана: имя ветки
в теге образа ничего не доказывает, SHA может оказаться от её базы. Не доехало за ~15 минут — логи
пода (скил `stand-logs`) и попросить пользователя глянуть сборку (ссылка печатается, если задан
`github_actions_url`).

## Повтор той же ветки

Новый пуш = новый тег (время в имени), CI соберёт заново. Старые теги не удалять и не двигать.

## Настройка

`scripts/config.local.json` (пример — `scripts/config.example.json`; другой путь — переменная
`DEPLOY_TO_STAND_CONFIG`). Без него скрипт не работает: правила CI у каждой команды свои.

| Поле | Что задаёт |
| --- | --- |
| `repos_root` | Папка с клонами репозиториев (`~` раскрывается; относительный путь — от корня проекта) |
| `own_stands` | Свои стенды: на них катить без отдельного согласия |
| `never_target` | Куда не катить никогда, по умолчанию `["prod", "uat"]` |
| `release_substring` | Подстрока, которая в CI катит прод, по умолчанию `release` |
| `ci_tokens` | Все слова, на которые реагирует CI хоть одного репозитория (стенды, `prod`, `uat`): имя ветки с чужим стендом опасно |
| `max_tag` | Предел длины тега (тег образа = тег + `-sha7` ≤ 128), по умолчанию 100 |
| `dead_runners` | Имена раннеров, которых больше нет: ветка со старым workflow повиснет в очереди |
| `github_actions_url` | Шаблон ссылки на сборки, `{repo}` подставляется |
| `repos.<имя>` | `kind: tag` — `path`, `default`, `wf` (файл workflow), `blob` (первые 12 символов `git rev-parse origin/main:.github/workflows/<wf>`, пусто — не следить), `tag_tokens` (стенды, на которые CI катит по тегу), `stops` (стенд → причина отказа), `special` (слово → предупреждение), `image_tag_unverified` |
| `repos.<имя>` | `kind: project` — у каждого проекта свой workflow: `projects.<код>` с `wf`, `blob`, `stands`; необязательный `catalog` (`code`, `wf`, `blob`, `stands`) — общий workflow, который триггерится тегом `<код>-…` |
| `excluded` | Репозитории, которые скил не катит, и почему |

`tag_tokens` и `blob` снимаются с workflow default-ветки: какие слова в имени тега он матчит и куда
катит. Проверка логики без сети: `python3 scripts/test_stand_tag.py`.
