# Карта окружений и контекст проверки

Зачем: в проверках регулярно забывают про локали и второй домен, про то, что публика ходит в
регионы с базой только на чтение, что нужный сервис живёт только на одном стенде, и что ветка
принесла переменную, которой нет в gitops стенда. Этот скил — одно место, где это записано, и
чеклист, который применяется сам.

**Сама карта — в `local.md` рядом с этим файлом** (пример формата — `local.example.md`): домены,
регионы, стенды, кто на каком стенде живёт, нюансы прода, на которых уже обжигались. Это данные
вашей инфраструктуры, в git они не идут. Нет `local.md` — скажи пользователю, что карта не заполнена,
и предложи собрать её по примеру; без карты чеклист ниже всё равно проходится, но ответы на пункты
берутся у пользователя.

У каждого факта в карте стоит основание и дата: проверено запросом, взято из gitops или кода, или
это предположение. Перепроверить хосты карты: `bash .claude/skills/stand-topology/tools/probe-hosts.sh`
(только GET; список хостов — `tools/hosts.local.txt`, пример — `tools/hosts.example.txt`). Нашёл
расхождение — поправь карту и дату.

## 1. Чеклист перед проверкой (обязателен)

Перед планом проверок пройти пункты и **вывести в чат блок «Контекст проверки»** — 5–7 строк, чтобы
пользователь поправил до прогона. Шаблон:

```
Контекст проверки
- Сервис/ветка → контур: backend `feat/x` → qa1 (мой) · образ на стенде = <tag/SHA>?
- Локали и домены: затронуты все / только EN / … → домены: …
- Регион и запись: центр / регион; пишет ли код в базу → в регионах с репликой молча не работает
- Зависимости контура: общие для всех стендов сервисы, раздача сборки с CDN, …
- env: `env-diff` → новых переменных нет / N новых: X (есть default), Y (нет ни в коде, ни в gitops qa1)
```

Пункты и откуда брать ответ:

1. **Контур.** Стенд из вопроса; если не назван — свои стенды пользователя из `local.md`; остальные
   общие, прод — только с согласия. Сверить, что на стенде именно нужная сборка: тег образа пода и
   SHA (имя ветки в теге ничего не доказывает).
2. **Локали и домены.** Правка, которая трогает текст, мету, роуты, фиды, сайтмапы, по умолчанию
   затрагивает **все** прод-домены из карты. Явно назвать, какие проверяем и почему этого достаточно.
   RTL-локали, локали с особыми разделами, второй домен того же контента — из карты. Домен, которого
   нет на стендах, проверяется на проде только чтением.
3. **Регион и запись.** Если публичный трафик прода идёт в ближайший регион, а у регионов база
   только на чтение, любой код с записью в базу (воркеры, счётчики, `SELECT … FOR UPDATE`) в регионах
   молча не работает, а деплой при этом зелёный. Какой регион ответил и как развести центр и регион —
   в карте. Админские ручки обычно показывают центр.
4. **Зависимости контура.** Что ещё участвует и где живёт: сервисы, которые есть только на одном
   стенде и общие для всех; общий для стендов AI-роутер или очередь; раздача сборки с CDN или из
   бакета (меняет CORS, кэш и то, что видно в логах пода). Всё это — в карте.
5. **Переменные окружения.** Для ветки сервиса, который деплоится через gitops, **всегда** запустить
   `python3 tools/env-diff/env_diff.py --service <svc> --stand <стенд> [--ref <ветка>]` (на Windows —
   `python`) и вынести результат в блок. Новая переменная без default и без значения в gitops — блокер
   прогона, пока её не добавят (куда именно — скрипт печатает). Инструмента нет — строка
   `env: N/A — почему` и ручная сверка `.env.example` ветки с values стенда.
6. **Данные стенда отстают от прода** — перед baseline сверить, есть ли на стенде нужный контент;
   эталон поведения — прод (только чтение).
7. **Если проверка на проде** — пробежать раздел карты «нюансы прода»: кэш CDN, волна 404 чанков
   после выкатки, перегрузка от краулеров, особенности GraphQL. Прежде чем назвать что-то дефектом
   прода, сверить с этим списком.

**Дальше — тест-план** (скил `qa-evidence`, раздел «Тест-план»): этот блок — его первая часть, а пункты
2–5 становятся строками «Покрытия» (локали и домены, регион и запись, окружение). До плана прогон не
начинается.

## 2. Что держать в карте (`local.md`)

Разделы по образцу `local.example.md`:

- **Прод:** публичные домены по локалям (со статусом и датой проверки); адреса CMS, API, CDN; регионы
  прода — namespace, кластер, база на запись или реплика; откуда прод берёт env.
- **Нюансы прода, на которых уже обжигались:** кэш, ложные «баги», правила запросов к API — каждый
  пункт с датой и ссылкой на разбор.
- **Стенды:** шаблон хостов; таблица «стенд → фронт, CMS, особенности»; какой сервис на каких стендах
  включён; свои и общие стенды; что на стенде не так, как на проде.
- **Не существуют:** хосты из старых документов, которые больше не отвечают, — с датой, чтобы ими не
  пользоваться.

## 3. Как поддерживать карту

- Новый факт — строкой в нужную таблицу, с основанием и датой. Старую строку не удалять молча: если
  хост умер — переносить в «не существуют» с датой.
- Раз в релизный цикл или при подозрении — `probe-hosts.sh`, сравнить с таблицами.
- Крупные разборы — отдельным документом или заметкой, а в карте — ссылка, а не копия разбора.
